# Apexatix Pro Bot

## Market data providers

All requested asset candles use Twelve Data first and Finnhub second. Keyed fallbacks then try StockData.org for US-listed stocks, followed by Finage and Financial Modeling Prep (FMP) for the requested instrument. StockData.org's intraday feed covers US-listed stocks only and returns minute bars that are aggregated into 15-minute candles. If those feeds are unavailable for a crypto asset, public 15-minute spot candles from Coinbase, Kraken, and Binance are tried, followed by Yahoo Finance through the open-source Python `yfinance` package. Binance is used only for the exact requested quote pair; for example, `BTC/USDT` maps to Binance's `BTCUSDT`, and `BTC/USD` is never silently converted to USDT. Non-crypto assets skip the exchange feeds and fall back to Yahoo Finance. Slash-separated FX/metals symbols map to Yahoo's `BASEQUOTE=X` tickers (for example `EURUSD=X`); crypto symbols map to `BASE-QUOTE` (for example `BTC-USD`); symbols without a slash are used as Yahoo tickers directly. Provider intraday access and history limits vary by instrument and plan; an unavailable ticker is never substituted with a different instrument. Fallback data cannot be independently verified against the primary feeds, so source status remains unavailable and conservative strategy checks will continue to HOLD.

Exchange API references: [Coinbase candles](https://docs.cdp.coinbase.com/exchange/reference/exchangerestapi_getproductcandles), [Kraken OHLC](https://docs.kraken.com/api/docs/rest-api/get-ohlc-data/), and [Binance klines](https://developers.binance.com/docs/binance-spot-api-docs/rest-api/market-data-endpoints#klinecandlestick-data).

Keyed provider references: [StockData.org documentation](https://www.stockdata.org/documentation), [Finage forex intraday documentation](https://finage.co.uk/docs/api/forex/forex-intraday-prices), and [Financial Modeling Prep documentation](https://site.financialmodelingprep.com/developer/docs).

### Shared serverless cache (Upstash Redis)

The market-data API uses Upstash Redis when `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN` are configured. Cached closed-candle results are shared across serverless instances, dashboard users, and the scheduled scanner. A short-lived Redis lock prevents simultaneous cache misses from issuing duplicate provider requests; cache entries expire at the next expected 15-minute candle close. If Redis is not configured or temporarily unavailable, the API logs the cache problem and continues with the market-data providers.

To configure the free Upstash Redis database with Vercel:

1. Create a Redis database in the [Upstash Console](https://console.upstash.com/) and keep it on the Free plan. Select a region close to the Vercel deployment.
2. Open the database details and copy its **REST URL** and **REST token**. Treat the token as a password.
3. In Vercel, open the project **Settings → Environment Variables**. Add `UPSTASH_REDIS_REST_URL` with the REST URL and `UPSTASH_REDIS_REST_TOKEN` with the REST token. Select every environment where the dashboard is deployed (Production, and Preview if applicable).
4. Save the variables and redeploy the latest deployment so the serverless function receives them.
5. Open the deployed dashboard and run a scan. Check the Upstash database metrics for commands; simultaneous users requesting the same symbol/timeframe should reuse the same cached result. After a new 15-minute candle closes, one request refreshes the cache and the other callers reuse it.

The scheduled `/api/bot` scan also uses this Redis database for a bounded rolling history of its confirmed BUY/SELL signals. Each event stores the decision snapshot and reference levels; later closed candles are checked for stop/target hits, or a time exit after 12 candles. If one candle touches both stop and target, it is counted conservatively as a stop. The dashboard reads `/api/trade-history` every five minutes and shows completed count, win rate, average/net R, pending count, and breakdowns by symbol, regime, confidence, and action. With browser alerts enabled and the dashboard open, new local BUY/SELL/WATCH signals and newly resolved scheduled-scanner outcomes can also appear as Windows notifications; colored symbols distinguish BUY (green), SELL (red), and WATCH (amber). Native notification styling is controlled by Windows.

History is evaluation-only and never tunes strategy thresholds or places orders. Outcomes are simulated from candle OHLC values, do not represent broker fills, and exclude fees, spread, and slippage. Redis keeps at most 250 signal/outcome records in one key with a 90-day expiry; the rolling window can be shorter if the cap is reached. This bounded design uses the existing Redis database only. [Upstash's current pricing page](https://upstash.com/pricing/redis) lists 250 MB and 500,000 commands per month for its Free tier; market-data caching and all other database use share those limits, so check the Upstash usage page after deployment. If Redis is unavailable, scanning continues, but historical outcomes cannot be recorded or displayed.

The REST credentials are read only by the serverless API; do not add them to browser code, commit them, or put them in DNS settings. The browser may keep polling every minute, but provider requests are shared and normally happen once per closed 15-minute candle for each symbol. Without configured Upstash credentials, provider requests bypass this shared cache.

When Twelve Data succeeds and `FINNHUB_API_KEY` is configured, Finnhub is queried as an independent comparison source. If a provider fails, the asset-specific fallback chain is tried for the same instrument. Configure `TWELVE_DATA_API_KEY`, `FINNHUB_API_KEY`, `STOCKDATA_API_TOKEN`, `FINAGE_API_KEY`, and `FMP_API_KEY` as server-side environment variables for local development and deployment. StockData.org's intraday feed is for US-listed stocks, and StockData describes its data as indicative and not appropriate for trading; Finage and FMP intraday symbols, history, and access depend on each account's plan. Styvio is intentionally excluded from this provider chain. Coinbase, Kraken, and Binance endpoints are public and require no API key; availability and supported spot pairs vary by exchange. These exchange feeds apply only to crypto and represent exchange-specific prices, which may differ from broker prices. There is no free intraday fallback feed substituted for spot FX or metals, so unsupported instruments remain unavailable instead of using a futures or unrelated proxy. `requirements.txt` installs yfinance for the Python function. Do not expose provider keys in browser code. When all configured sources fail, the dashboard displays **“No data found due to API.”**; detailed provider errors are kept out of the user-facing message.

## Market scanning and alerts

The dashboard defaults to XAU/USD, BTC/USD, EUR/USD, and AUD/USD; silver is not in the default watchlist, but users can add assets manually. It refreshes closed-candle market data while open and auto-scan is enabled. Trend direction is determined by a two-of-three vote from EMA9/EMA21, MACD versus its signal, and RSI above/below 50; requiring all three to agree could leave a sustained trend unrecognized when RSI lagged. The default strategy and scheduled scanner use that rule for the 45-minute regime and entry checks, then require at least two of the 15m, 30m, and 45m trends to align. This produces BUY setups only in a confirmed bullish trend and SELL setups only in a confirmed bearish trend. Each dashboard card now labels its detected 45m trend independently of whether there is a complete entry setup. The optional **Trend + Dual-TF RSI Confluence** strategy adds a pullback requirement: the 45m trend and selected entry-timeframe EMA/MACD must agree, then 15m and 30m RSI must both confirm an oversold pullback (≤30 and ≤38) for BUY or overbought pullback (≥70 and ≥62) for SELL.

The **Conservative Day-Trade Pullback** option applies stricter entry gates: both feeds must verify the same completed candle, volume data must be available and not unusually low, the 30m and 45m two-of-three EMA/MACD/RSI trend votes must agree, the selected entry timeframe's EMA/MACD must confirm that direction, and 15m RSI must reset to 40–<50 for BUY or >50–60 for SELL. The general Dual-TF RSI, EMA/MACD, and Bollinger/RSI strategies also require the signal direction to agree with the confirmed 45m trend, preventing counter-trend BUYs in bearish regimes and counter-trend SELLs in bullish regimes. A bearish 45m trend can produce SELL setups when the selected strategy's own entry conditions confirm; if any required trend or entry signal is missing or conflicts, the result is an explanatory HOLD. While the dashboard is open, it checks market data every minute and can issue a deduplicated browser **WATCH** notification when the 45m direction is established and the 15m EMA or MACD is converging toward a possible entry. A WATCH is an early heads-up, not a trade signal; BUY/SELL still requires the full strategy rules. The GitHub Actions workflow calls `/api/bot` every five minutes; when `DISCORD_WEBHOOK_URL` is configured, it sends confirmed BUY/SELL and recent WATCH events only when the latest closed candle is no more than five minutes old, avoiding stale reports and repeated alerts for the same candle. Configure repository secrets `VERCEL_URL` and `CRON_SECRET` for the scheduled workflow. BUY/SELL signals use the existing ATR-based invalidation reference (normally 1.5× ATR, refined by nearby support/resistance where justified) and a 2:1 target; this does not calculate position size or guarantee limited losses. Alerts include a rationale, timestamp, and market/indicator snapshot.

When both feeds return candles, a same-candle price disagreement above 0.5% for traditional markets or 1% for crypto suppresses entries. Source verification and provider details continue to inform signal validation but are omitted from dashboard cards and summaries.

Signals are held during quiet volatility (ATR below 0.02% of price), an erratic candle (range above 3 times the recent median), or available volume below half its recent average. Volume feeds are not universal; when volume is unavailable, confidence is capped rather than treating missing volume as adequate. These diagnostics influence decisions but are omitted from dashboard cards. Regimes are classified as Trending, Ranging, Volatile, or Quiet. The default trend-following strategy uses a 2-of-3 timeframe alignment threshold; the optional RSI, EMA/MACD, and Bollinger/RSI strategies retain their adaptive weighted composite score of at least 0.45. Confidence reflects cross-timeframe alignment and data quality.

Stops start at 1.5 ATR and may be widened just beyond nearby recent support/resistance; targets are recalculated at 2R. Recent closed candles are also used for simplified directional backtests, with trade count, win rate, and net R calculated internally. The trend-following historical sample uses the EMA/MACD/RSI direction rule; live entries additionally require the multi-timeframe alignment above. Backtests use a maximum 12-candle holding window, treat same-candle stop/target touches conservatively as stop-outs, and exclude fees, spread, and slippage. They are informational only: thresholds remain fixed and are not auto-tuned. Diagnostic inputs such as regime, ATR, volume availability, feed verification, support/resistance reasoning, and backtest metrics inform filtering and confidence but are not displayed in the dashboard cards.

Confidence is a confluence label, not a probability or a guarantee. Browser notifications are optional and require enabling the trade-alert control in the dashboard. Actionable signals in the dashboard transparency log are displayed as structured cards, colored green for BUY, red for SELL, and amber for WATCH; native browser notification colors remain controlled by the operating system. Dashboard scans pause when the page is closed or auto-scan is disabled; the separately configured GitHub Actions scan continues on its five-minute schedule. Alerts are advisory: the bot does not execute orders or calculate position size. The user must confirm executable broker prices, instrument contract specifications, and account-specific risk limits before acting.

Routine HOLD results are grouped into a single summary per manual scan rather than one log entry per asset. Auto-scan does not repeatedly log unchanged no-setup outcomes; individual HOLD reasons remain visible on the asset cards, while actionable signals and data-quality warnings remain in the transparency log.
